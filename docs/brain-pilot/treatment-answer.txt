### 2. Exposing Kanban API on games-only: gate, consumer, impact, invariant

**Current gate:** `handler`, `scripts/preview-service.mjs:107–108`:

```js
if (servesApps() && url.pathname.startsWith('/api/kanban/')) {
  return handleKanbanRequest(req, res, { repoRoot });
}
```

With `PREVIEW_SURFACE=games`, it does not delegate. The request falls through to static routing, whose allowlist rejects `/api/kanban/...`, producing **403** (`safeStaticPath`, `:63–81`; `serveStatic`, `:83–87`).

**Immediate downstream consumer:** `handleKanbanRequest` in `scripts/kanban-bridge.mjs:828–978`. Broadening the prefix gate exposes the existing route family—not just bridge health or a new game-specific API. That includes board/task reads, diagnostics and mutation endpoints, subject to their existing guards.

Further downstream:
- `loadBoard` → fixture data or `liveBoard`; the latter invokes `scripts/kanban-readonly.py` through Python (`:515–539`).
- `runHermesKanban` → `runHermesRaw` → Hermes subprocess (`:498–513`).
- UI eligibility independently checks board read-only/write flags and execution state in `apps/kanban/app.js:71–76`.

**First-order impact:** Games clients gain reachability to Kanban data/routes. In live mode, requests may reach the existing task backend; enabling API reachability does not itself serve `/apps/kanban/`. Do not change `servesApps()` merely to expose an API, because that also broadens app/static routing and advertised links.

**Invariant:** Reachability must remain separate from write/execution capability.
- `resolveMode` (`bridge:91–96`): explicit fixture/live overrides; otherwise port 4174 or truthy `CI` selects fixture, else live.
- `readOnlyMode`/`writesEnabled` (`:98–104`): writes require live mode and an explicitly false-parsed `KANBAN_READONLY`; default is read-only.
- Fixture remains read-only even with `KANBAN_READONLY=false`.
- `requireWritable` (`:563–574`) enforces this server-side.
- `executionEnabled`/`requireExecution` (`:106–115`) introduce a further execution flag requirement.

The games unit sets `PREVIEW_SURFACE=games` but contains no write/execution enable flags. The app unit explicitly enables them (`deploy/systemd/user/agent-app-preview.service:12–16`). These are tracked templates, not proof of effective live environment.

**Tests:** Update the games API expectation in the surface-separation test (`:157`) only if exposure is intentionally changed, while retaining app-static denial. Extend games-mode coverage to capability reporting and rejected mutations. Preserve `kanban fixture mode honestly disables writes despite the operator flag` (`:161–179`): it asserts disabled capability flags, POST **423**, and disabled UI creation despite `KANBAN_READONLY=false`.

### 3. Does a successful health probe prove commit, enabled writes, or no external dependencies?

**No, on all three.**

`healthPayload`, `scripts/preview-service.mjs:46–61`, returns:
- Constant `ok: true`
- Service name
- Configured surface
- Conditional advertised app/game URLs

`handler` serves it with 200 at `/healthz` independently of surface (`:122–123`). It contains **no commit identity, write/execution flags, task-store probe or dependency inventory**. Even an invalid surface can return successful health.

Probe guarantees differ:
- `healthcheck` (`:133–139`) requires a successful HTTP response and parseable JSON. It does not validate `ok`, service identity, revision or capabilities.
- Capture tooling’s `healthOk` (`scripts/capture-game-video.mjs:18–25`) checks **HTTP success only**, without parsing JSON.
- `ensurePreviewServer` (`:45–58`) reuses any server passing that check. `main` separately loads the **local** game registry and navigates the configured target (`:79–97`); health does not establish that target’s content matches the local checkout.

`GET /api/kanban/health` is different: `handleKanbanRequest:835–847` reports configuration-derived mode, board, write/execution flags and allowed-write names. It **does not exercise the task backend**, establish successful persistence or identify a deployed commit.

Source establishes connections to Python and Hermes subprocesses, contradicting any inference that successful generic health proves a dependency-free application. It does not establish whether those dependencies currently work, or enumerate all external services/clients.

**Tests:** Existing generic-health and surface-separation tests check payload fields and routing. The fixture-write test checks one capability-enforcement case. None of these inspected assertions proves deployed identity or complete dependency health. The service-template test (`tests/preview-workflow.spec.mjs:203–228`) checks tracked file contents; despite its title, its file loop checks `isFile()`, not executable bits or installation.
